# 识别优先 Demo 交付参数

日期：2026-10-09

本文件把“识别率 Demo”和“六用户系统实时性实验”分开交付。识别率
诊断使用本交接包中的同一份 LCA 权重、Exp23 bundle 和 VCTK 测试语音；
它不是六路并发吞吐结果。

## 1. 推荐运行配置

| 参数 | 当前值 |
| --- | --- |
| 输入采样率 | 16 kHz |
| 声道 | 单声道 |
| LCA RVQ 层数 | 3 |
| codebook size | 1024 |
| 每个索引位宽 | 10 bit |
| 编码分块 | 1.5 s（24,000 samples） |
| 说话人识别窗口 | 3.0 s（48,000 samples） |
| 识别更新步长配置 | 1.0 s（实际受 1.5 s 分块和队列节拍约束） |
| Exp23 输入 | `codes_waveform` |
| 原始模型输出空间 | 110 个身份类别 |
| Demo 决策空间 | `p225,p226,p227,p228,p229,p230` |
| 分类温度 | 1.01877269160619 |
| `verified` 显示阈值 | 0.65 |
| LCA 设备 | `cuda`（不可用时回退 CPU） |
| Exp23 分类器设备 | 当前为 CPU |
| 信道条件 | `clean` |

六人候选集是在推理时屏蔽另外 104 个类别，不改变 110 类模型权重，
也不是重新训练的六分类模型。

## 2. 识别率诊断结果

测试集为六个固定 VCTK 身份，每人 15 条，共 90 条三秒语音。每条语音
按指定分块编码、解码，再用 Exp23 做一次 Top-1 判断。

| 条件 | 正确数 | 总数 | Top-1 |
| --- | ---: | ---: | ---: |
| 110 类 + 0.5 s | 76 | 90 | 84.44% |
| 六人候选 + 0.5 s | 89 | 90 | 98.89% |
| 六人候选 + 1.5 s | 90 | 90 | 100.00% |

这组结果是识别-focused 本地诊断，不包含 Router 排队、六路同时发送或
声学播放。

## 3. 交互 Demo 运行命令

推荐配置：

```powershell
python group_client.py `
  --user_id B `
  --speaker_id_enable `
  --speaker_classifier_bundle <bundle_dir> `
  --no_play
```

上面的命令是识别诊断模式，不打开声卡。若需要听恢复语音，交互入口默认会
尝试打开播放设备；对于 1.5 s 分块，建议显式把抖动上限提高到至少一个分块
加目标缓冲：

```powershell
python group_client.py `
  --user_id B `
  --speaker_id_enable `
  --speaker_classifier_bundle <bundle_dir> `
  --max_lat 1.75
```

`--max_lat 1.75` 是播放配置建议，不是新配置的实测实时延迟。

恢复 110 类、0.5 秒开放集基线：

```powershell
python group_client.py `
  --user_id B `
  --speaker_id_enable `
  --speaker_classifier_bundle <bundle_dir> `
  --speaker_classifier_candidates all `
  --chunk_seconds 0.5 `
  --no_play
```

## 4. 实时性和系统参数

### 4.1 当前协议参数

| 参数 | 值或口径 |
| --- | --- |
| 目标抖动缓冲 | 0.25 s |
| 最大抖动缓冲 | 0.80 s |
| 1.5 s 配置的名义单向缓冲预算 | 1.75 s（1.5 + 0.25） |
| 识别首次上下文 | 约 3 s 语音 |
| 识别更新间隔 | 配置为 1 s；实际受 1.5 s 分块和队列节拍约束 |
| 播放 | 交互入口默认开启；识别诊断显式 `--no_play`；正式 metrics 默认关闭 |
| 网络 | 单机 TCP loopback |
| 载荷码率 | 约 1.504 kbit/s（索引载荷，不含协议开销） |

默认 `max_lat=0.80 s` 小于 1.5 s 解码块；播放开启时，抖动队列超过上限会
丢弃旧样本并回到 `target_lat=0.25 s`，因此可听 Demo 应显式提高
`--max_lat`。名义单向缓冲预算不是实测端到端声学延迟。播放关闭时，只能报告
采集/回放调度到解码完成的边界。

### 4.2 交接包已有的 0.5 s 系统实测

以下数据来自原交接包的 GPU 六用户系统实验，条件是 **110 类 + 0.5 s**，
不能直接当作新推荐配置的实测值：

- 轮流发送：预测覆盖率 100%，有效 Top-1 85.56%。
- GPU LCA 编码 P95 15.18 ms，解码 P95 18.71 ms。
- GPU 轮流发送采集到解码 P95 约 1.79 s。
- GPU 轮流发送分类推理 P95 约 1.59 s。
- GPU 六路同时发送：预测覆盖率 16.44%，端到端正确率 14.44%，
  采集到解码 P95 约 10.54 s。
- 30 分钟六路稳定性：进程未崩溃，但存在接收队列丢弃和期限失败。

这些结果说明旧条件下的主要瓶颈是并发排队和 CPU 分类回退，而不是
单纯的分类 Top-1。

## 5. 恢复语音和音质参数

“恢复语音”需要同时交付重建配置、时序处理规则和质量结果：

| 参数 | 当前值或口径 |
| --- | --- |
| 解码输出采样率 | 16 kHz（除非显式设置 `--out_sr`） |
| 解码输出声道 | 单声道 |
| 解码方式 | 每个收到的 RVQ 块独立解码，再按源块位置拼接 |
| 块长度 | 1.5 s Demo 配置为 24,000 samples；论文基线为 8,000 samples |
| 缺失块 | 保留原时间位置并补零，不删除时间空隙 |
| 跨块对齐 | 不做相关性搜索或时间平移 |
| 信道条件 | 默认 `clean`；扰动条件必须单独标注 |
| 播放 | 交互默认开启；诊断显式 `--no_play`；开启时记录播放队列、丢弃和欠载 |
| 音质指标 | STOI、PESQ-WB、mel-L1 |
| 音质统计范围 | 每个接收端、每条源语音、全 3 秒时长 |

当前交接包已有的旧条件 GPU 轮流发送音质结果为：

- STOI：0.8229
- PESQ-WB：1.7443
- mel-L1：0.8942

这些音质数值来自 **110 类 + 0.5 s** 的旧系统测量，不能直接当作
六人候选 + 1.5 s 的新配置结果。新配置还应同时报告：

- 成功重建语音条数和音质计算失败条数；
- 收到块、按时解码块、缺失块、补零块；
- 每条语音的 STOI/PESQ-WB/mel-L1，而不只给总平均；
- 若开启播放，播放队列长度、欠载次数和播放回调延迟。

## 6. 新推荐配置仍需单独测量的项目

如果要把 1.5 s + 六人候选作为正式系统性能结果，还需要重新记录：

- 首次正确识别延迟：中位数、P95、最大值；
- 实际识别更新间隔和同流身份切换响应；
- 编码、传输、解码、分类各阶段 P50/P95；
- 预测覆盖率、有效 Top-1、端到端正确率；
- 接收队列积压、丢弃、截止期失败；
- CPU、GPU 利用率、显存、RSS；
- STOI、PESQ-WB、mel-L1；
- 单源载荷码率和应用层总流量。

在这些指标重新跑完之前，推荐配置可以宣称“识别率诊断达到 100%”，
但不能宣称“六路实时性能达到 100%”或“完整声学端到端延迟已验证”。
